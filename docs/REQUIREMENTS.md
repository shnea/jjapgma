# 요구사항 정리

처음 시작하거나 구현 결과를 크게 바꾸는 정보가 부족할 때 사용한다. 명확한 기능 수정에는 별도 기획 절차를 만들지 않는다.

## 최소 브리프

[프로젝트 설정](PROJECT_SETUP.md)의 제품 항목에 아래 내용을 적는다.

- 누가 어떤 문제를 해결하는가?
- 이번에 완료할 사용자 흐름과 성공 조건은 무엇인가?
- 이번 범위에서 제외할 기능은 무엇인가?
- 저장할 데이터와 로그인·권한이 필요한 지점은 어디인가?
- 이미 정해진 기술·디자인·예산·일정·배포 제약은 무엇인가?

확정 사실과 가정을 구분한다. 실제로 필요한 질문만 한 번에 소수로 묻는다. 프로젝트 이름·로컬 포트처럼 쉽게 바꿀 수 있는 값은 임시 기본값을 기록하고 진행할 수 있다.

## 진행 판단

| 상황 | 행동 |
| --- | --- |
| 사용자가 정리나 계획만 요청함 | 브리프와 선택지를 정리하고 구현하지 않는다 |
| 범위가 충분한 구현 요청 | 짧게 가정을 알리고 구현한다 |
| 핵심 제품 동작이 미정 | 해당 동작을 묻고 관련 없는 준비·조사는 계속한다 |
| 도메인·운영 계정만 미정 | 로컬 구현·테스트는 진행하고 외부 설정은 미정으로 둔다 |
| 다른 사람의 데이터 삭제 등 되돌리기 어려운 실행이 미정 | 구체적인 영향과 복구안을 준비하고 해당 실행 전 확인한다 |

질문 목록, 긴 계획서, 전 기능의 Storybook 컴포넌트를 모두 완성해야 개발할 수 있다는 조건을 만들지 않는다.

## 작업으로 옮기기

첫 흐름을 구현하기 전에 [연동 지침](INTEGRATIONS.md)을 탐색해 기능별 자체/연동 범위를 정한다. 첫 흐름 하나를 UI → API → 데이터 → 검증까지 연결하는 크기로 나눈다. 사용자 관점의 완료 조건을 이슈나 PR에 적는다. 지속적인 설계 선택만 [결정 기록](DECISIONS.md)에 남긴다.

에이전트에게 전달할 예:

```text
AGENTS.md와 docs/PROJECT_SETUP.md를 확인해.
이번 작업: <사용자가 할 수 있어야 하는 일>
완료 조건: <확인 가능한 결과>
제약: <유지할 기술, 수정 범위, 기한>
미정 사항은 영향이 큰 것만 묻고, 나머지는 작은 가정을 기록해 진행해.
구현 후 관련 검증과 문서 갱신까지 마쳐줘.
```
